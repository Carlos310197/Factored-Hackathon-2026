# Infrastructure as Code Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Terraform for the pipeline's AWS and Snowflake infrastructure, applied by GitHub Actions through one secretless trust chain (GitHub OIDC → AWS role `gha-deploy` → Snowflake workload identity).

**Architecture:** Two stacks. `bootstrap/` (applied once from a laptop, state then migrated to S3) creates the state bucket, the GitHub OIDC provider, role `gha-deploy`, Snowflake user `TF_DEPLOY` and the organizer keys in SSM. `platform/` (applied only by CI) creates the serving bucket, the Snowflake↔S3 integration and IAM role, and all Snowflake account objects. RAW/META tables stay in the pipeline's SQL scripts.

**Tech Stack:** Terraform ≥ 1.10 (local 1.15.2; `terraform test` with `mock_provider`), `hashicorp/aws` ~> 6.0, `snowflakedb/snowflake` ~> 2.21, GitHub Actions (`aws-actions/configure-aws-credentials@v4`, `hashicorp/setup-terraform@v3`), Python 3.12 + `uv` for the smoke test.

**Spec:** `docs/design/2026-10-01-infra-iac-design.md`

## Review Focus

1. **Fork or foreign-branch PR assuming `gha-deploy`.** Only the two `sub` values above may assume it; a `ref:refs/heads/feature-x` push must be denied. Pinned in Task 1 (`trust_policy_exact_subjects`).
2. **Snowflake trust drift.** The `snowflake-serving` trust policy must use the integration's own IAM user ARN and external ID, never a hard-coded value; if the integration is recreated the role follows. Pinned in Task 2 (`serving_role_trusts_integration`).
3. **Organizer secret leaking into CI.** CI never needs `.env`: the SSM parameters ignore value changes and `platform/` reads them via data sources. Pinned in Task 1 (`ssm_values_ignored_after_create` checks the lifecycle via a plan with different values) and Task 3 (workflow has no `secrets.` reference).
4. **Plan on a PR applying.** The PR job must only `plan`; `apply` only on `push` to `main`. Pinned in Task 3 (`test_workflow_apply_only_on_main`).
5. **Overlapping applies.** Two merges in a row must not run `apply` concurrently. Pinned in Task 3 (`test_workflow_has_concurrency_group`).

```bash
# One-time bootstrap from a laptop (and again only if the trust chain changes, e.g. repo rename).
# Needs: `aws sso login --profile hackathon-sso` and the snow CLI connection `sbx`.
set -euo pipefail
cd "$(dirname "$0")"

env_get() { grep -E "^$1=" "$ENV_FILE" | head -1 | cut -d= -f2-; }

export TF_VAR_organizer_key_id="$(env_get AWS_ACCESS_KEY_ID)"
export TF_VAR_organizer_secret="$(env_get AWS_SECRET_ACCESS_KEY)"

terraform init -input=false
terraform apply "$@"
```

```hcl
  for_each = local.databases
  name     = each.key
```
